## Phase 1 · 可行性验证（必须先做，3 项硬验证）

> **原则：先验证，再实现。** 三项中任一项不通过，直接切换保底路线，不做无用开发。

### 前置操作（需你确认）

1. 保存手头工作；
2. **正常退出** WorkBuddy（确保托盘无残留进程）；
3. 以带调试端口方式启动：

```powershell
& "<WorkBuddy 安装目录>\WorkBuddy.exe" --remote-debugging-port=19222
```

> 端口仅监听本机回环，验证完请**立即恢复常规启动方式**。

### 验证项 1：调试端口是否可用

```bash
curl -s http://127.0.0.1:19222/json/version
```

- ✅ **通过标准**：返回含 `"Browser"` / `"webSocketDebuggerUrl"` 的 JSON。
- ❌ **不通过**：连接被拒 → 客户端屏蔽了该 flag（或存在单实例锁未退出干净）→ 转保底路线。

### 验证项 2：能否命中渲染进程 target

```bash
curl -s http://127.0.0.1:19222/json
```

- ✅ **通过标准**：列表中能找到 `type: "page"` 且 `url` 指向 WorkBuddy 主界面的 target，并带有 `webSocketDebuggerUrl`。
- 记录该 `webSocketDebuggerUrl` 供后续使用。

### 验证项 3：RPC 通道是否仍存在且可调用（核心）

连上 target 后执行：

```js
// 1) 确认桥接入口存在
typeof window.__wbInvoke
// 期望："function"

// 2) 只读查询签到状态（不产生任何副作用）
await __wbInvoke('auth:getCheckinStatus')
// 期望：返回含 today_checked_in / streak_days / daily_credit 的对象
```

- ✅ **通过标准**：`__wbInvoke` 为 function，且 `auth:getCheckinStatus` 返回正常数据 → **主路线成立**。
- ❌ **不通过**：`__wbInvoke` 为 undefined（preload 变更）→ 检查 `window.vscode` / `window.mcp` 等其它暴露名，或转保底路线。
- ⚠️ **通道更名**：若报 unknown channel，用 `02` 附录的检索方法重新定位通道名（客户端改名不影响方案结构）。

### 验证期安全约束

- 仅调用**只读**接口 `auth:getCheckinStatus`；**不在验证阶段**触发 `claimDailyCheckin`（避免与当日手动签到冲突）。
- 不打印、不落盘任何令牌或设备指纹。

## Phase 2 · 实现签到脚本

### `scripts/checkin-via-cdp.js`（已提供骨架）

流程：

1. 探测 `127.0.0.1:19222/json`，找到主界面 target；
2. 建立 WebSocket（Node 22 内置 `WebSocket`，**零依赖**）；
3. `Runtime.evaluate` 执行：
   - 先 `auth:getCheckinStatus` 判断是否已签到 → 已签到直接返回「今日已签到」（**幂等**）；
   - 未签到则 `auth:claimDailyCheckin`；
4. 归一化结果，追加一行到 `签到历史.md`，写 `logs/checkin.log`；
5. 失败经 WxPusher 推送（沿用旧项目通知方式，SPT 另行配置，不入库）。

### 结果归一化规则（沿用旧项目）

| 判定 | 依据 |
|------|------|
| 成功 | 返回含积分/连续天数 |
| 已签到 | `today_checked_in = true` 或返回「已签到」类 code |
| 失败 | 通道报错 / 端口不可用 / 未登录 |
| 未知 | 其它 |

## Phase 3 · 幂等、定时与降级

### 幂等

脚本自带「先查后签」；重复执行不产生副作用。多点补签策略沿用旧项目：**09:00 / 12:00 / 15:00 / 18:00 / 21:00**。

### 定时方式

使用 **WorkBuddy 原生自动化**（`automation_update`，禁用 crontab / launchd / 任务计划程序），prompt 极简：

```jsonc
{
  "name": "Buddy加油站签到(CDP)",
  "scheduleType": "recurring",
  "rrule": "FREQ=DAILY;BYHOUR=9,12,15,18,21;BYMINUTE=0",
  "cwds": "<项目根目录>",
  "status": "ACTIVE",
  "prompt": "运行 node scripts/checkin-via-cdp.js 完成 Buddy 加油站签到，只回复一句话结论。"
}
```

### 降级策略（重要）

定时触发时客户端可能**未以调试端口运行**。脚本按序处理：

1. 探测 19222 → 有则直接签到（最佳）；
2. 无端口但进程在运行 → **不做危险操作**，记录「需手动签到」并推送提醒（可选：提示用户重启为调试模式）；
3. 可选增强：脚本自行「退出 → 带参数拉起」——**默认关闭**，避免打断用户工作，需显式开关启用。

## Phase 4 · 回归与回退

- **上线检查单**：连续 3 天签到成功；重复执行返回「已签到」；客户端未开时正确降级不刷屏。
- **回退**：本方案不改动客户端任何文件，回退即「停止自动化 + 恢复常规启动方式」。
- **版本守护**：客户端升级后先跑 Phase 1 验证项 3，确认 `__wbInvoke` 与通道名仍有效。

## 附录 · 通道名变更时的检索方法

客户端升级后若 RPC 通道改名，用以下方式重新定位（本评估即用此法）：

1. 解包 asar 头部索引，按关键词（如 `claimDailyCheckin`、`CLAIM_DAILY_CHECKIN`）反查命中的 bundle 文件；
2. 在命中的文件内取关键词上下文，读取：
   - 通道常量（`contract.js` 一类）
   - 处理器注册（`handler-registry.js` 一类）
   - preload 暴露名（`exposeInMainWorld`）
3. 用新的通道名替换脚本中的常量即可，方案结构不变。

> 参考脚本 `scripts/probe-cdp.js` 内含端口探测逻辑，可独立运行确认环境状态。
