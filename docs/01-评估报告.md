# 01 · 评估报告

> 评估对象：WorkBuddy 桌面端 5.6.2 的「Buddy 加油站 → 签到领积分」
> 评估日期：2026-09-25 ｜ 结论：**模拟点击可行，推荐"调试协议 + 内部 RPC"路线**

---

## 一、背景与现状

老方案（旧项目，另存于本地一独立目录）使用「本地读令牌 → 直连签到 API」方案，自 2026-09-01 起连续成功至 09-24。

| 日期 | 结果 | 详情 |
|------|------|------|
| 2026-09-24 | 成功 | 领取100积分，连续9天 |
| 2026-09-25 09:00 | 失败 | 获取令牌失败 |
| 2026-09-25 09:57 | 失败 | 未找到登录态 |
| 2026-09-25 10:07 | 失败 | 令牌加密暂不支持(需手动签到) |

**关键判据：不是账号问题，也不是 token 过期，而是客户端升级后存储与接口形态同时换了。**

## 三、根因分析：为什么老方案失效

### 3.1 令牌改为非对称加密（第一道墙）

登录态文件结构（仅列字段名，未读取任何凭据值）：

```
auth: {
  accessToken:  { $wbEncrypted: 1, envelope: str(2448) }
  refreshToken: { $wbEncrypted: 1, envelope: str(1408) }
  ...
}
```

实现位于主进程 `packages/at-rest-crypto`，识别两种信封：

- `$wbEncrypted=1` + `envelope` → **标准信封**
- `$wbEncrypted=1` + `envelope` + `scheme:"asym-v1"` → **非对称信封**

**非对称加密意味着公钥加密、私钥不落盘**。老脚本（含上游 `decrypt-token.js`）只会按明文字符串读取，遇到信封即失效——这是**存储格式升级，不可绕过**，不是 token 过期。

### 3.2 新增设备风控头（第二道墙）

签到请求在客户端内部的实际构造（主进程 `AccountProvider.claimDailyCheckin`）：

```js
const session = this.authenticationManager.currentSessionSubject.getValue();
if (!session?.auth?.accessToken || !session?.account?.uid)
  throw new Error("claimDailyCheckin: no active session");

const endpoint = this.productManager.getEndpoint().replace(/\/+$/, "");
const response = await this.http.post(
  `${endpoint}/v2/billing/meter/daily-checkin`,
  {},
  { headers: await this.buildHeadersWithTuringToken(session) }   // ← 关键
);
```

其中：

```js
var TURING_SHIELD_ID_HEADER   = "X-Device-Token";
var TURING_SHIELD_ERROR_HEADER = "X-Device-Token-Error";
```

即请求必须同时携带：

1. `Authorization: Bearer <accessToken>` —— 被非对称信封锁住
2. `X-Device-Token: <Turing 设备指纹>` —— 由客户端内置风控 SDK（`main/turing-sdk.js`）生成

**两道墙叠加，外部脚本复刻 API 的路线被彻底封死。**

### 3.3 接口路径升级（第三道墙）

| 用途 | 现接口 | 老脚本用的接口 |
|------|--------|----------------|
| 查状态 | `POST /v2/billing/meter/checkin-activity-status` | `POST /billing/meter/checkin-status` |
| 签到 | `POST /v2/billing/meter/daily-checkin` | `POST /billing/meter/daily-checkin` |

路径与字段（`today_checked_in` / `streak_days` / `is_streak_day` 等）均已变更。

## 四、签到按钮的真实调用链（评估的核心依据）

从客户端 bundle 中还原出的完整链路：

```
用户点击「Buddy加油站 → 签到领积分」
  │  data-track-id = "avatar_menu_fuel_station"
  ▼
渲染进程 (renderer / React UI)
  │  AccountProvider.claimDailyCheckin()
  │  → this.sendBackendRequest(BACKEND_REQUEST_TYPES.CLAIM_DAILY_CHECKIN)
  │  → channel.callMethod("__backend__", { type:"backend", params:{ type:"auth:claimDailyCheckin" } })
  ▼
preload 预加载层（contextBridge 暴露）
  │  createIpcInvoke(ipcRenderer)  ——  业务 channel 复用固定通道 "wb:invoke"
  │  暴露为全局：window.__wbInvoke(channel, context, ...args)
  ▼
主进程 handler-registry
  │  authClaimDailyCheckin: invoke(AUTH_RPC_CHANNELS.CLAIM_DAILY_CHECKIN, CHECKIN_RPC_TIMEOUT_MS)
  ▼
主进程 AccountProvider（持有会话 + 风控 SDK）
  │  POST {endpoint}/v2/billing/meter/daily-checkin
  │  Headers: Authorization: Bearer … + X-Device-Token: …
  ▼
腾讯官方接口 → 返回积分 / 连续天数
```

### 关键证据（客户端 bundle 内原文位置）

| 证据 | 所在文件 |
|------|----------|
| `AUTH_RPC_CHANNELS.CLAIM_DAILY_CHECKIN = "auth:claimDailyCheckin"` | `/main/contract.js` |
| `authClaimDailyCheckin: invoke(..., CHECKIN_RPC_TIMEOUT_MS)` | `/main/handler-registry.js` |
| `exposeInMainWorld("__wbInvoke", exposedWbInvoke)` | `/preload/index.js` |
| `createIpcInvoke(ipc, { invokeChannel:"wb:invoke" })` | `/preload/index.js`（`workbuddy-core/wb/boundary/transport/ipc.ts`） |
| `BackendProvider.claimDailyCheckin() → httpService.post("/billing/meter/daily-checkin")` | `/main/tar.js`、`/renderer/assets/ui-docs-viewer-*.js` |
| `X-Device-Token` / Turing 风控 | `/main/tar.js`、`/main/turing-sdk.js` |
| i18n：`account.menu.fuelStation = "Buddy加油站"`、`account.menu.fuelStation.claimCredits = "签到领积分"`、`account.menu.fuelStation.claimed = "今日已签到"` | `/renderer/assets/zh-cn-*.js` |

### 这条链路对自动化的意义

> **点击按钮 = 最终落到 `__wbInvoke("auth:claimDailyCheckin")`。**

也就是说：只要能**在渲染进程里执行一段 JS**，就能完成签到——不需要令牌、不需要设备指纹、不需要模拟鼠标轨迹。鉴权完全由客户端自己完成。

## 五、候选路线可行性对比

| 维度 | **A. CDP + 内部 RPC** | **B. 真·UI 点击（UIA/坐标）** | **C. 直连 API** |
|------|----------------------|------------------------------|-----------------|
| 原理 | 带 `--remote-debugging-port` 启动 → 连 WebSocket → `Runtime.evaluate` 调 `__wbInvoke` | 定位窗口控件或坐标，模拟鼠标点击菜单与按钮 | 读本地 token 后 POST |
| 是否需解密令牌 | 否（客户端自己鉴权） | 否 | **是（已不可解密）** |
| 是否需伪造风控 | 否 | 否 | **是（不可伪造）** |
| 稳定性 | **高**（不依赖 UI 布局/焦点） | 低（依赖前台、DPI、界面改版、菜单浮层） | — |
| 前置条件 | 客户端需**带参数重启**一次并保持运行 | 客户端需**运行且窗口可见** | — |
| 失败模式 | 端口未开 / 单实例锁 / 版本校验 | 点击错位、菜单未渲染、锁屏 | 必然失败 |
| 触碰客户端文件 | 否（仅启动参数） | 否 | 否 |
| 合规风险 | 低（本地调试协议） | 低 | — |
| **结论** | ✅ **推荐** | ⚠️ 保底方案 | ❌ 淘汰 |

### 补充说明：为什么"真·UI 点击"不是首选

1. **Electron 的 UIA 树默认不完整**：Chromium 内容区通常需要 `--force-renderer-accessibility` 才向 UIA 暴露 DOM 节点，否则只能拿到窗口级别句柄 → 只能退化为坐标点击。
2. **坐标点击对环境极敏感**：分辨率/缩放/主题/多屏都会导致偏移；在 RDP 会话或锁屏状态下，自动化点击必然失败。
3. **菜单是浮层**：`avatar_menu_fuel_station` 属于头像下拉菜单，需先展开菜单再命中目标项，时序与命中率都难保证。

### 关于"CDP 需要重启客户端"这一代价

- Electron 应用若**未在启动时**带 `--remote-debugging-port`，运行中无法从外部附加上调试器（无 attach 入口）。
- 因此需要：退出客户端 → 带参数重新启动 → 保持运行。这对**定时任务**意味着：定时触发时若客户端未以该参数运行，则需脚本自行拉起。
- 缓解措施见 `02-实施方案.md` 的 **Phase 3**（探针脚本自动判断，未开调试端口则降级为提醒）。

---

## 六、结论

1. **"模拟点击"目标可以实现**，但推荐实现方式为 **CDP 触发内部 RPC（等价点击）**，而非逐像素真实点击。
2. **纯 API 复刻（老项目路线）已无恢复可能**，除非官方为自动化场景签发专用令牌/接口。
3. **保底方案**：若 CDP 因企业策略/版本限制无法启用，退回 UIA/坐标点击，接受其脆弱性并**只在交互式桌面会话下运行**。
4. **老项目保留**：`workbuddy签到` 目录与 `workbuddy-checkin` 技能不删除，作为历史记录与回退参考；本项目独立演进，互不影响。

---

## 七、风险与合规声明

| 风险 | 等级 | 缓解 |
|------|------|------|
| 调试端口暴露 | 中 | 仅绑 `127.0.0.1`；仅验证期与签到窗口期开启；不写入浏览器扩展/公开配置 |
| 客户端升级导致 RPC 改名 | 中 | 探针脚本每日校验通道是否仍存在，失效即告警而非静默失败 |
| 误触他人账号 | 低 | 脚本仅运行于本机已登录的单一账号 |
| 违反用户协议 | 低 | 仅限本人每日签到，不批量、不刷分、不转售 |
| 令牌/设备指纹泄露 | 低 | 本方案**完全不读取**令牌与 `X-Device-Token`，不存在落盘与外传路径 |

> 本评估仅为技术可行性分析。使用前请确认符合 WorkBuddy 用户协议；使用者自行承担风险。
